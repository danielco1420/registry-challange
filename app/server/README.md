Server-only code lives here in `*.server.ts` modules so it never reaches the client bundle.

- `config.server.ts`: typed env config, validated with Valibot when the server build loads. It's the only place that reads `process.env`; import `config` from it. `parseEnv(source)` is the pure parser behind it.
- `dockerhub.server.ts`: the Docker Hub client and the only module that knows Docker Hub URLs. `dockerHub.get(request, schema)` takes a typed request (never a URL or path) and a Valibot schema, and returns the validated body or throws an `UpstreamError` (`not_found`, `rate_limited`, `unavailable`, `bad_payload`). Timeout, User-Agent, one retry honoring `Retry-After`. Tests: `dockerhub.server.test.ts` (`pnpm test`), against a local HTTP server and MSW.
- `dockerhub.schemas.server.ts`: Valibot schemas for every Docker Hub response we read (search v4 and suggestions, legacy search, repository, tags, tag, org, user). Lenient on display fields, strict on identity and type. A body that fails one makes the client throw `bad_payload` with `issuePath` (e.g. `$.results[3].name`). Tests: `dockerhub.schemas.server.test.ts`, against the recorded `fixtures/dockerhub/`.
- `normalize.server.ts`: pure functions from validated payloads to the DTOs in `app/lib/dto.ts` (`toSearchPage`, `toLegacySearchPage`, `toRepoDetails`, `toTag`, `toTagsPage`, `toOrgPublisher`, `toUserPublisher`), handling `library`, pull-count labels vs numbers, and missing logo/description/size. Tests: `normalize.server.test.ts`.
- `search.server.ts`: `searchRepositories` / `suggestRepositories`: v4, falling back to the legacy `/v2/search/repositories/` when v4 fails its schema (non-empty, unfiltered queries only). Tests: `search.server.test.ts`, through the real client against MSW fixtures.
- `budget.server.ts`: proxy-wide upstream budget (ADR-0003), a sliding window of `UPSTREAM_BUDGET_PER_MIN` upstream attempts per 60 s. The shared `dockerHub` client takes a slot per attempt, retries included, and fails with `budget_exhausted` (nothing sent) when there is none. Tests: `budget.server.test.ts`.
- `upstream.server.ts`: `getCached(key, ttlSeconds, fetcher)`, the facade every route and loader uses to read Docker Hub data (cache + client + budget). Returns `{ value, status, ageMs, degraded }`; throws `UpstreamUnavailableError` when there is no cached value and upstream fails or the budget is spent. `cachedJson(data, result, ttlSeconds)` and `upstreamUnavailableResponse(error)` build the 200 (`X-Cache`, `Age`, `Cache-Control`) and the 503 (`Retry-After`, `no-store`). Tests: `upstream.server.test.ts`.
- `api.server.ts`: shared plumbing for the `/api/*` proxy resource routes (`app/routes/api.*.ts`). `handleApi(request, handler)` applies the rate limit and turns any failure into a JSON error; `proxyJson({ key, ttlSeconds, load })` reads through `getCached` and answers 200 / 404 (a `null` from `load`, cached) / 503; `orNotFound(promise)` maps an upstream 404 to `null`; `rejectWrite(request)` is every proxy route's `action` (a JSON `405`). Tests: `api.server.test.ts`, and the routes end to end in `app/routes/api-routes.test.ts`.
- `rateLimit.server.ts`: per-client rate limit (ADR-0003). Call `enforceRateLimit(request)` at the top of a resource route or page loader; it throws a 429 `Response` with `Retry-After` when the client is over `RATE_LIMIT_MAX` per `RATE_LIMIT_WINDOW_MS`. The module comment explains how the client IP is resolved (`TRUST_PROXY_HOPS`).
